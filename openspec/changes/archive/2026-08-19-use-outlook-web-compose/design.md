## Context

現在のフロントエンドは `buildMailtoUrl` で `mailto:` URLを組み立て、確認ボタンのクリック時に `window.location.href` へ設定した後、メール作成日時をAPIへ記録する。メール送信自体は外部のOutlookに委譲しており、M365の認証情報、Graphアクセストークン、SMTP認証情報は保持していない。

Outlook on the web は外部オリジンであるため、laborman からサインイン状態、作成画面の読込、送信元、送信完了を検知できない。既存と同様に、アプリが保証する範囲はメール内容の生成と作成画面を開く操作までとする。

## Goals / Non-Goals

**Goals:**

- OSの既定メールクライアントに依存せず、会社のMicrosoft 365 Outlook on the webへ下書き内容を渡す。
- Outlookのcompose deep linkがCC/BCCを反映しない場合でも、登録された全宛先をToへ統合して自動入力する。
- labormanを元のタブに残し、メール作成済み記録と送信済み自己申告の導線を継続して利用できるようにする。
- 日本語、改行、複数宛先を欠損なくURLへエンコードする。
- 外部ページを開けない場合にも、既存のコピー導線で作業を継続できるようにする。

**Non-Goals:**

- Microsoft Graph APIまたはSMTPを使用した自動送信。
- M365へのサインイン、セッション更新、利用アカウント選択の自動化。
- Fromの指定、Outlook on the webの読込完了または送信完了の検知。
- Outlookの作成画面でTo・CC・BCCの区分を維持すること、およびBCC宛先を他の受信者から秘匿すること。
- OutlookデスクトップアプリまたはOSの既定メールクライアントを選択できる設定の追加。

## Decisions

### D1: Outlook on the web のcompose deep linkを直接生成する

メール作成URLのベースを `https://outlook.office.com/mail/deeplink/compose` とし、`to`・`subject`・`body` をクエリパラメータとして渡す。実機検証で `cc` パラメータが作成画面へ反映されないことを確認したため、登録上のTo・CC・BCCをこの順で統合して `to` へ渡し、`cc` / `bcc` パラメータは生成しない。

この方式は自動入力を維持できる一方、CC/BCCの区分を失い、BCCを含む全宛先が受信者全員に表示される。利用者がこのトレードオフを選択したため、確認画面と運用文書で常に明示する。

ブラウザ側の `mailto:` プロトコルハンドラ設定を変更する方式は、端末・ブラウザごとの設定や組織ポリシーに依存するため採用しない。Graph APIで下書きを作成する方式は、アプリ登録、OAuth、権限同意、トークン管理が必要となり、本変更の目的に対して過剰なため採用しない。

### D2: URL生成はフロントエンドの純粋関数へ集約する

既存のメール下書き型を入力として、Outlook on the web 用URLを返す純粋関数へ置き換える。To・CC・BCCの配列をこの順で連結し、各値は `encodeURIComponent` で個別にエンコードし、複数宛先の区切りはリテラルのカンマを使用する。スペースが `+` に変換される実装差を避けるため、`URLSearchParams` によるフォーム形式のシリアライズは使用せず、現在と同じ `%20` 形式を維持する。

URL生成ロジックとベースURLを1か所に閉じ込めることで、Outlook側の仕様変更時にも局所的に差し替えられるようにする。

### D3: 新しいタブはユーザー操作の同期処理内で開く

確認ボタンのクリックを直接の起点として、非同期API処理を待つ前にOutlook on the webを新しいタブで開く。外部タブには `noopener` と `noreferrer` 相当の分離を適用し、元のlabormanタブへの参照を渡さない。

同じタブで遷移すると、メール作成日時を記録するAPI通信が中断される可能性があり、送信済み自己申告へ戻る導線も失われる。API完了後にタブを開く方式は、ブラウザのポップアップブロック対象になりやすいため採用しない。

### D4: 外部ページの結果は推測せず、既存の自己申告モデルを維持する

Outlook on the webを開く操作を実行した後に、既存の `markMailCreated` APIでメール作成済みを記録する。クロスオリジンのOutlook画面が実際に読み込まれたか、送信されたかは検知しない。送信完了は元のタブにある自己申告チェックでのみ扱う。

確認画面には、会社のM365アカウントで事前にサインインすること、Fromを確認すること、登録上のCC/BCCもToとして全員に表示されることを明示する。サインイン期限切れ、アカウント違い、URL長、タブのブロックに備え、統合後の宛先を含む項目別コピーを元のタブに残す。

## Risks / Trade-offs

- [M365セッション切れ時にサインイン遷移を挟み、入力値が欠落または変形する可能性がある] → 事前サインインを案内し、入力済みにならない場合は再試行またはコピーで復旧できるようにする。
- [複数のM365アカウントにサインインしていると意図しないFromが選ばれる可能性がある] → URLではFromを指定せず、確認画面とOutlook作成画面で会社アカウントを確認するよう案内する。
- [ブラウザが新しいタブをブロックする可能性がある] → ユーザークリックの同期処理内で開き、失敗時も元のタブのコピー導線を利用可能にする。
- [長い本文またはOutlook側の変更によりdeep linkが正しく処理されない可能性がある] → 長いURLの警告とコピー導線を維持し、URL生成を1か所へ集約して差し替えやすくする。
- [CC/BCCの区分が失われ、特にBCC宛先が受信者全員に開示される] → 全宛先がToになることを設定画面・確認画面・README・セットアップガイドへ明示し、送信前の宛先確認を必須の運用とする。
- [デスクトップ版Outlookを前提にしていた利用者の操作が変わる] → UIと利用手順をOutlook on the web前提へ統一し、ロールバック可能なフロントエンド変更として提供する。

## Migration Plan

1. URL生成関数とテストをOutlook on the web用へ変更する。
2. メール作成ダイアログの遷移処理、案内、ボタン文言、フォールバック文言を変更する。
3. 自動テストとフロントエンドビルドを実行し、サインイン済みの会社M365アカウントで登録上のTo・CC・BCCがすべてToへ統合され、件名・本文・改行・Fromが正しいことを実機確認する。
4. README、アーキテクチャ、セットアップガイドを新しい運用へ更新する。

データ移行とバックエンドの段階的切り替えは不要である。問題が発生した場合は、フロントエンドのURL生成と起動処理を `mailto:` 方式へ戻すことでロールバックできる。
