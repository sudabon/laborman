# Spec Delta

## Purpose

laborman が算出したドラフトを、ホストのエージェントが zac の業務報告画面へ安全に入力・保存し、その結果を記録・通知するための機能。誤登録を防ぐ段階的な実行モードと安全ガードを含む。

## ADDED Requirements

### Requirement: 一連の実行

エージェントは、`laborman-agent run [--date D] [--mode M] [--headed] [--force]` で、対象日（既定は前営業日）について次の順に処理しなければならない（SHALL）：zac 保存成功日時の確認（設定済みなら終了コード `0` でスキップ。`--force` で無視）→ zac への到達性の確認 → 出退勤実績が未登録なら人事メールの取込 → ドラフトの取得と検証 → zac への入力 → モードに応じた保存 → 結果の記録と通知。`laborman-agent register` は人事メールの取込を行わずに zac 以降の処理だけを行わなければならない（SHALL）。

#### Scenario: 登録済みの日

- **WHEN** 対象日の zac 保存成功日時が設定済みの状態で `run` を実行する
- **THEN** エージェントは zac を開かず、終了コード `0` で終了する

#### Scenario: VPN 未接続

- **WHEN** zac の到達性確認用 URL に 5 秒以内に接続できない
- **THEN** エージェントは状態 `vpn_unreachable` を記録し、終了コード `2` で終了する

### Requirement: 勤怠と休憩の入力

エージェントは、zac の勤怠欄に、出退勤実績の出勤・退勤を出社時刻・退社時刻として入力しなければならない（SHALL）。休憩は、工数明細の行ではなく勤怠欄の休憩の時間数として入力しなければならない（SHALL）。入力する値は、ドラフトの「出退勤の範囲内の休憩」の合計を時間帯で分けたもの（22:00〜24:00 の部分は「休憩（22〜24時）」、24:00〜29:00 の部分は「休憩（24〜29時）」、それ以外は「休憩」）を `H:MM` で表したものとしなければならない（MUST）。該当のない時間帯の欄は空にする。休憩を工数明細の行として入力してはならない（MUST NOT）。

#### Scenario: 昼休憩を入力する

- **WHEN** 2026-10-09 の出退勤が 08:29–18:38 で、休憩 12:00–13:00 が記録され、検証結果に error がない日に `run` を実行する
- **THEN** エージェントは出社時刻に 8:29、退社時刻に 18:38、休憩に 1:00 を入力し、工数明細には休憩の行を追加しない

#### Scenario: 深夜の休憩を分けて入力する

- **WHEN** 休憩 12:00–13:00 と 23:30–24:15 が記録された日に `run` を実行する
- **THEN** エージェントは休憩に 1:00、休憩（22〜24時）に 0:30、休憩（24〜29時）に 0:15 を入力する

### Requirement: 工数の入力

エージェントは、ドラフトの入力行ごとに zac の作業登録を開き、作業内容・案件（ジョブ ID で検索して選ぶ）・売上項目・所要時間・備考を入力して登録しなければならない（SHALL）。作業内容・案件・売上項目は、zac の選択肢の表示名がドラフトの値と一致するものを選ばなければならず（MUST）、一致する選択肢がない場合は入力を中止し、状態 `failed` に一致しなかった項目を記録しなければならない（MUST）。作業登録の「登録」は、zac の画面上の工数明細への追加であり、zac への保存ではない。

#### Scenario: 入力行を作業登録で入れる

- **WHEN** ドラフトに「プロジェクト作業・2602028・プロジェクトサポート（2026／10）・5:00・- 設計レビュー」の入力行がある
- **THEN** エージェントは作業登録で作業内容「プロジェクト作業」、案件 2602028、売上項目「プロジェクトサポート（2026／10）」、所要時間 5:00、備考「- 設計レビュー」を入力して登録し、工数明細に 1 行を追加する

#### Scenario: zac に売上項目がない

- **WHEN** ドラフトの売上項目「プロジェクトサポート（2027／01）」が zac の売上項目の選択肢にない
- **THEN** エージェントは入力を中止し、保存せずに `failed` と一致しなかった売上項目を記録して通知する

### Requirement: 実行モード

エージェントは、実行モード `dry_run`・`assist`・`auto` を持たなければならない（SHALL）。モードの既定値は laborman の設定から取得し、`--mode` で上書きできなければならない（SHALL）。

- `dry_run`：zac の画面に入力してスクリーンショットを保存し、保存せずに状態 `dry_run_done` を記録する。zac は作業登録で追加した工数明細を自動保存するため、`dry_run` でも工数明細は zac に残る（出退勤・休憩は保存しない限り残らない）。同じ日を再実行すると既存の入力として `already_registered_in_zac` になる
- `assist`：入力した画面を表示したまま、利用者の保存操作を最大 15 分待つ。保存完了の表示を確認できたら `succeeded`、時間切れなら `awaiting_user` を記録する
- `auto`：保存操作を行い、保存完了の表示を確認する

#### Scenario: dry_run

- **WHEN** 実行モード `dry_run` で、検証結果に error がない日に `run` を実行する
- **THEN** エージェントは zac の画面に入力行を入力したあとで出退勤を入力し（zac は明細の追加ごとに勤怠欄を入れ直すため）、休憩を休憩専用フォームに入力し、スクリーンショットを保存し、保存操作を行わずに `dry_run_done` を記録する

#### Scenario: assist で利用者が保存する

- **WHEN** 実行モード `assist` で入力後、利用者が zac の画面で保存する
- **THEN** エージェントは保存完了の表示を確認して `succeeded` を記録し、対象日の zac 保存成功日時を設定する

### Requirement: 検証結果による制御

エージェントは、ドラフトに `error` がある場合、どのモードでも zac の保存操作を行ってはならず（MUST NOT）、状態 `validation_failed` を記録して通知し、終了コード `3` で終了しなければならない（MUST）。`warning` がある場合、`auto` は `dry_run` として動作し、その旨を通知しなければならない（MUST）。

#### Scenario: error のある日

- **WHEN** 対象日のドラフトに `UNCOVERED_TIME`（error）がある状態で、実行モード `auto` で `run` を実行する
- **THEN** エージェントは zac を操作せず、`validation_failed` を記録・通知して終了コード `3` で終了する

#### Scenario: 休憩が記録されていない日

- **WHEN** 対象日のドラフトに `BREAK_MISSING`（error）がある状態で `run` を実行する
- **THEN** エージェントは zac を操作せず（業務報告の入力を中止し）、`validation_failed` を記録して「休憩が記録されていません」と対象日を通知し、終了コード `3` で終了する

#### Scenario: warning のある日の auto

- **WHEN** 対象日のドラフトに `TASK_OUTSIDE_ATTENDANCE`（warning）がある状態で、実行モード `auto` で `run` を実行する
- **THEN** エージェントは保存操作を行わずに `dry_run` として入力とスクリーンショットまでを行い、`auto` から降格したことを通知する

### Requirement: 既存入力の非上書き

エージェントは、zac の対象日に既存の入力がある場合、入力・保存を行ってはならない（MUST NOT）。状態 `already_registered_in_zac` を記録して通知し、終了コード `3` で終了しなければならない（MUST）。

#### Scenario: zac で手入力済みの日

- **WHEN** 対象日の zac 業務報告画面にすでに明細が入力されている
- **THEN** エージェントは何も入力せず、`already_registered_in_zac` を記録・通知して終了コード `3` で終了する

### Requirement: 操作範囲の制限

エージェントは、zac の「確定」「確定解除」「月報確定」「申請」「承認依頼」その他保存以外の確定操作を行ってはならない（MUST NOT）。自動化の上限は「保存」とし、「確定」は利用者が zac で行う。

#### Scenario: 保存後の確定ボタン

- **WHEN** `auto` で保存が完了し、画面に「確定」ボタンが表示される
- **THEN** エージェントは「確定」ボタンを操作せずに処理を終える

### Requirement: 保存結果の確認

エージェントは、保存完了の表示を確認できた場合にのみ状態 `succeeded` を記録しなければならない（MUST）。確認できない場合、またはエラー表示を検知した場合は `failed` とし、スクリーンショットのパスを記録しなければならない（MUST）。

#### Scenario: 保存完了を確認できない

- **WHEN** `auto` で保存操作をした後、保存完了の表示が一定時間内に現れない
- **THEN** エージェントは `failed` とスクリーンショットのパスを記録し、通知して終了コード `3` で終了する

### Requirement: 実行履歴

システムは、エージェントのすべての実行結果を、対象日・モード・状態・入力した内容のスナップショット・メッセージ・スクリーンショットのパス・エージェントのバージョン・開始/終了日時とともに記録しなければならない（SHALL）。状態は `requested`・`cancelled`・`running`・`succeeded`・`dry_run_done`・`awaiting_user`・`validation_failed`・`needs_login`・`vpn_unreachable`・`hr_mail_not_found`・`already_registered_in_zac`・`failed` のいずれかとする。状態 `succeeded` が記録された場合、システムは対象日の zac 保存成功日時を設定しなければならない（MUST）。実行履歴は勤務日で絞り込んで取得できなければならない（SHALL）。

#### Scenario: 成功を記録する

- **WHEN** エージェントが実行開始を `running` で記録し、その後 `succeeded` に更新する
- **THEN** システムは実行履歴を更新し、対象日の zac 保存成功日時を設定する

#### Scenario: メール未着を記録する

- **WHEN** `run` で出退勤実績が未登録のため人事メールを探したが見つからない
- **THEN** エージェントは `hr_mail_not_found` を記録し、終了コード `2` で終了する

### Requirement: 画面からの実行依頼

システムは、「本日の報告」画面の「この日を zac に登録」操作で、表示中の勤務日の実行依頼を実行履歴に状態 `requested` として記録しなければならない（SHALL）。同じ勤務日に `requested` または `running` の実行履歴がある場合は `409` を返し、依頼を重複して記録してはならない（MUST NOT）。`requested` の依頼は利用者が取り消せなければならず（SHALL）、取り消した依頼は `cancelled` とする。

エージェントは、`laborman-agent process-requests` で `requested` の依頼を古い順に取得し、依頼ごとに `requested` から `running` への更新（取得済みでなければ失敗する条件付きの更新）に成功したものだけを、その勤務日について `run` と同じ流れ（人事メールの取込 → ドラフト → zac 入力）で実行し、結果を同じ実行履歴に記録しなければならない（SHALL）。実行モードは設定の実行モードとする。依頼がなければブラウザを起動せずに終了コード `0` で終了しなければならない（SHALL）。システムは、`process-requests` を 1 分間隔で起動する launchd の設定例と導入手順を提供しなければならない（SHALL）。

#### Scenario: 画面から実行を依頼する

- **WHEN** ユーザーが 2026-10-09 の本日の報告で「この日を zac に登録」を押す
- **THEN** システムは 2026-10-09 の実行履歴を `requested` で記録し、パネルに依頼中であることを表示する

#### Scenario: エージェントが依頼を実行する

- **WHEN** 2026-10-09 の依頼が `requested` の状態で `process-requests` が起動する
- **THEN** エージェントは依頼を `running` にしてから 2026-10-09 の出退勤の取込と zac 入力を行い、結果（例：`dry_run_done`）を同じ実行履歴に記録する

#### Scenario: 依頼の重複

- **WHEN** 2026-10-09 の依頼が `requested` のまま、もう一度「この日を zac に登録」を押す
- **THEN** システムは `409` を返し、新しい依頼を記録しない

#### Scenario: 依頼がない

- **WHEN** `requested` の依頼がない状態で `process-requests` が起動する
- **THEN** エージェントはブラウザを起動せず、終了コード `0` で終了する

### Requirement: zac のサインイン

zac は独自のログイン ID とパスワードでサインインし、セッションは翌日には切れる。エージェントは、zac のサインイン画面を検知した場合、設定のログイン ID と、利用者が macOS キーチェーンに登録したパスワード（設定のサービス名で検索）を読み出してサインインしなければならない（SHALL）。パスワードは設定ファイル・DB・ログ・実行履歴・通知に書き出してはならず（MUST NOT）、キーチェーン以外の場所に保存してはならない（MUST NOT）。キーチェーンにパスワードがない場合、またはサインイン後もサインイン画面のままの場合は、状態 `needs_login` を記録して通知し、終了コード `3` で終了しなければならない（MUST）。`laborman-agent login zac` で画面付きブラウザを開き、利用者が手動でサインインできなければならない（SHALL）。

#### Scenario: キーチェーンのパスワードでサインインする

- **WHEN** 前日のセッションが切れた状態で、キーチェーンにパスワードが登録されている状態で `run` を実行する
- **THEN** エージェントはサインイン画面にログイン ID とキーチェーンのパスワードを入力してサインインし、業務報告画面の入力を続ける

#### Scenario: パスワードが未登録

- **WHEN** キーチェーンにパスワードが登録されていない状態で、zac のサインイン画面が表示される
- **THEN** エージェントは `needs_login` を記録し、キーチェーンへの登録方法を案内する通知を出して終了コード `3` で終了する

### Requirement: VPN と zac の診断

エージェントは、`laborman-agent doctor` に zac の到達性（VPN 接続）、zac のプロファイル、キーチェーンにパスワードが登録されていること（値は表示しない）の確認を含めなければならない（SHALL）。

#### Scenario: VPN 未接続で診断する

- **WHEN** VPN に接続していない状態で `doctor` を実行する
- **THEN** エージェントは zac に到達できない旨を表示し、終了コード `3` で終了する

### Requirement: 定時実行

システムは、平日の朝に `laborman-agent run` を複数回（例：9:20・10:20・11:20・13:20）起動する launchd の設定例と導入手順を提供しなければならない（SHALL）。完了済みの日は即座にスキップされるため、複数回の起動で重複登録が起きてはならない（MUST NOT）。VPN 未接続などの再試行状態は、その日の最終回の起動でのみ通知しなければならない（SHALL）。

#### Scenario: 2 回目以降の起動

- **WHEN** 9:20 の起動で `succeeded` になった日に、10:20 に再度起動される
- **THEN** エージェントは zac を開かずに終了コード `0` で終了する

#### Scenario: 最終回まで VPN 未接続

- **WHEN** 9:20・10:20・11:20 は VPN 未接続で、13:20 の起動でも VPN 未接続
- **THEN** エージェントは 13:20 の起動でのみ VPN 未接続を通知する
